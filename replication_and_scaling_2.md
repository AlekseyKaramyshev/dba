**Задание 1**

Опишите основные преимущества использования масштабирования методами:

активный master-сервер и пассивный репликационный slave-сервер;
master-сервер и несколько slave-серверов;

**Решение**

Репликация со схемой master и ряд slave-серверов позволяет внося изменения систематизированно на одном master-сервере, распределять нагрузку запросов чтения на ряд readonly slave-серверов.

При разнесённых, по разным физическим хостам slave-серверам можно повысить производительность баз и добавить отказоустойчивость.

**Задание 2**

Разработайте план для выполнения горизонтального и вертикального шаринга базы данных. База данных состоит из трёх таблиц:

пользователи,
книги,
магазины (столбцы произвольно).
Опишите принципы построения системы и их разграничение или разбивку между базами данных.

`Пришлите блоксхему, где и что будет располагаться. Опишите, в каких режимах будут работать сервера.`


**Решение**

- Вертикальный шардинг

Shard1 ( ServerA ): таблица users ( данные пользователей ).

Обоснование: высокая частота операций записи (регистрация, обновление профиля), тесная связь с бизнес‑логикой авторизации.

Shard2 ( ServerB ): таблица shops ( данные магазинов ).

Обоснование: частые обновления информации о магазинах, геоданные, контакты; логическая связь с пользователями (например, заказы).

Shard3 ( ServerC ): таблица books ( данные книг ).

Обоснование: преимущественно операции чтения (поиск, каталог), редкие обновления (цены, описания).

Преимущества вертикального шардинга:

снижение конкуренции за ресурсы между разнородными данными;

оптимизация настроек сервера под конкретный тип нагрузки (например, больше ОЗУ для books);

упрощение резервного копирования и мониторинга.

Ограничения:

невозможность JOIN между таблицами на разных серверах без дополнительных механизмов;

необходимость координации транзакций между шардами.

---

- Горизонтальный шардинг


**Таблица users (пользователи)**

Ключ шардинга: user_id (диапазон) или region (география).

Варианты разбивки:

По диапазону user_id:

Шард 1: user_id от 1 до 1 000 000.

Шард 2: user_id от 1 000 001 до 2 000 000.

Шард 3: user_id от 2 000 001 до 3 000 000.

По региону:

Шард 1: пользователи из Европы (region = 'EU').

Шард 2: пользователи из Азии (region = 'AS').

Шард 3: пользователи из Америки (region = 'AM').

Равномерное распределение данных, простота маршрутизации по user_id.

**Таблица books (книги)**

Ключ шардинга: genre (жанр) или author_id.

Варианты разбивки:

По жанру:

Шард 1: художественная литература (genre IN ('Fiction', 'Novel')).

Шард 2: научно‑популярная литература (genre = 'Non‑Fiction').

Шард 3: учебная литература (genre = 'Academic').

По автору:

Шард 1: книги авторов с author_id % 3 = 0.

Шард 2: книги авторов с author_id % 3 = 1.

Шард 3: книги авторов с author_id % 3 = 2.

Группировка данных по смысловым категориям, снижение нагрузки на отдельные шарды при поиске по жанру.


**Таблица shops (магазины)**
Ключ шардинга: country (страна) или city (город).

Варианты разбивки:

По стране:

Шард 1: магазины в США (country = 'US').

Шард 2: магазины в ЕС (country = 'EU').

Шард 3: магазины в Азии (country = 'AS').

По городу:

Шард 1: магазины в Нью‑Йорке (city = 'NYC').

Шард 2: магазины в Лондоне (city = 'LON').

Шард 3: магазины в Токио (city = 'TYO').

Локальность данных, оптимизация геозапросов.

**Комбинированная схема шардинга**

- Этап 1. Вертикальное разделение:

Сервер A: users.

Сервер B: shops.

Сервер C: books.

- Этап 2. Горизонтальное разделение внутри каждого сервера:

На сервере A: 3 шарда для users (по user_id).

На сервере B: 3 шарда для shops (по country).

На сервере C: 3 шарда для books (по genre).

Итого: 9 шардов на 3 серверах.

**Режимы работы серверов**

Для каждого шарда используется репликация Master‑Slave:

Master: обработка операций записи (INSERT, UPDATE, DELETE).

Slave: обработка операций чтения (SELECT), резервное копирование.

Пример для users:

Master: запись новых пользователей.

Slave 1: авторизация, чтение профилей.

Slave 2: аналитика, бэкапы.

**Маршрутизация запросов**

Механизм: прокси‑сервер или шардинг‑менеджер, который:

Анализирует запрос (например, SELECT * FROM users WHERE user_id = 12345).

Определяет шард по ключу шардинга (user_id % 3).

Направляет запрос на нужный сервер и шард.

**Инструменты:**

PgBouncer (для подключения).

CitusDB (для распределённых запросов).

Самописный прокси на основе HAProxy.

**Обеспечение согласованности**
Методы:

Eventual Consistency: для операций чтения (допустима небольшая задержка репликации).

Двухфазный коммит (2PC): для транзакций, затрагивающих несколько шардов (редко).

Логическая репликация: синхронизация данных между Master и Slave.

**Преимущества предложенной схемы**

Масштабируемость: добавление новых шардов при росте данных.

Производительность: распределение нагрузки между серверами.

Отказоустойчивость: репликация защищает от сбоев.

Гибкость: возможность менять ключ шардинга без полной перестройки системы.

**Вертикальный шардинг**

```
+-----------------------------------------------------+
|               ПРИЛОЖЕНИЕ (клиент)                 |
|          (отправляет SQL-запросы)                |
+-----------------------------------------------------+
                       |
                       v
+-----------------------------------------------------+
|                 ПРОКСИ-СЕРВЕР                      |
|      (маршрутизация запросов по таблицам)           |
+-----------------------------------------------------+
        /             |               \
       v              v                v
+--------------+ +--------------+ +-----------------+
|  СЕРВЕР A    | |  СЕРВЕР B    | |  СЕРВЕР C       |
|  (users)     | |  (shops)     | |  (books)        |
|              | |              | |                 |
| +--------+   | | +--------+   | | +----------+    |
| | users  |   | | | shops  |   | | | books    |    |
| +--------+   | | +--------+   | | +----------+    |
+--------------+ +--------------+ +-----------------+
```
